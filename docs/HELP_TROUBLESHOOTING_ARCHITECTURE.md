# Help and Troubleshooting Architecture

## Goal
Give collectors immediate, friendly guidance without cluttering the main catalog. Help should grow naturally from real testing rather than becoming a giant manual before launch.

## Main help areas
- Getting Started.
- How to Add a Coin.
- How to Search and Filter.
- How to Edit or Finish an Unfinished Coin.
- Photos and Research.
- Backup and Export.
- Trash and Recovery behavior.
- Account, Profile, and Mascot settings.
- Professional/Dealer Mode when enabled.
- Troubleshooting.

## Guided help
The onboarding mascot teaches the first workflow step-by-step. After the first coin is completed, the mascot can offer to demonstrate another coin. The user can choose to continue practicing or proceed independently.

## Troubleshooting growth model
During testing, record recurring questions and confusion points. Convert useful recurring questions into concise troubleshooting entries. Avoid adding an entry for every isolated mistake.

Each troubleshooting entry should preferably contain:
1. What happened.
2. Why it may have happened, in plain language.
3. The simplest fix.
4. A next step if the fix did not work.

## Contextual help
Where practical, a Help action can open the relevant article for the screen the user is on. Do not require users to leave their workflow to understand a simple control.

## Accessibility
- Use plain language and readable text.
- Keep steps short.
- Avoid technical jargon.
- Important instructions must also be available as text, not only mascot animation.
- Help should remain usable with reduced motion enabled.

## Support requests
If the product eventually includes support/contact forms, protect users from account takeover or unauthorized recovery requests. Support should not expose private collection information unnecessarily, and any account/collection recovery procedure should use a documented verification process.

## Product boundary
Help content is part of the product experience but should not contain legal promises or guarantees. Privacy, security, data-loss, and liability language should be maintained separately in the appropriate legal documents and presented to users where required.
